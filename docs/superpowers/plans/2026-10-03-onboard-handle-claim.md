## Flow (new step 1b, after `register_borrower`)

1. `register_borrower` returns `handle` (null or existing), `suggested_handles`, `next_action`.
2. If `handle` is already set: show it, skip claiming.
3. If `next_action == "claim_handle"`: present `suggested_handles` to the borrower with the option of a custom handle.
4. Custom handle: optional `check_handle_availability`; offer alternatives if taken.
5. Confirmation STOP: show the exact handle that will be claimed and wait for an explicit yes. A claim is hard to undo and public, so this is the one allowed chat question in the otherwise no-question turn. It must not delay the wallet-proof / `request_borrower_token` chain (the borrower-token rule forbids a chat question before the token), so run the handle step after the token and workload key, or in parallel, never before them.
6. `claim_handle`, with `idempotency_key` (`{SKILL:sohopay-idempotency}`).
7. Soft gate: skipping or failing a claim never blocks onboarding.

### Soft-gate wording (draft, final)

> A handle is optional to transact: the borrower is always addressed by `borrowerId` and can pay, be authorized and repay without one. A handle only makes the borrower discoverable and resolvable by others. If the borrower declines, or a claim fails, finish onboarding and mention they can claim one later. Never block steps 2 to 7 on a handle.

### Draft step text (names and params PROVISIONAL)

> 1b. Handle (optional, soft gate) — if `register_borrower` returned `next_action: "claim_handle"`, show `suggested_handles` and let the borrower pick or propose one. For a custom handle, `check_handle_availability`. Show the chosen handle and wait for explicit confirmation, then `claim_handle`. See [references/handle-claim.md](references/handle-claim.md).
