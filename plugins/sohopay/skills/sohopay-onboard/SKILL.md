Execute the numbered workflow in **one turn**. Do not plan. Do not defer the workload key or `authorize_agent` until the first payment. **Before:** MCP connected (`{SKILL:sohopay-mcp-connect}`).

**Global failure rule:** If any fetch fails (non-2xx status, HTML content, or empty body), STOP. Do not improvise. Report the exact failed URL to the operator.

Canonical identity: **borrowerId = User.id (UUID)**. Pass `idempotency_key` on writes — `{SKILL:sohopay-idempotency}`.

0. `get_context` (catalog v8+) or `whoami` (v7) — skip *user* register if borrower exists; still `register_borrower` if this host has no `operational_agent_id`. On v8+, `get_context` returns `borrower_id` + credit + authorization directly; on v7 use `whoami` (field caveats: [references/whoami.md](references/whoami.md)) + `get_borrower_status`. `{SKILL:sohopay-bootstrap}`
1. `register_borrower` — creates this host’s terminal; store `operational_agent_id` + `terminal_id`. If it returns `spend_ready: false` with `next_actions` listing `CONNECT_WALLET` (and `CONNECT_BANK`), the borrower signed in without a wallet (phone or passkey): that is a registered borrower, **not an error**. Run steps 3, 4, 7 and 8 only (steps 2 and 6 need a wallet, and step 5’s workload key is pointless until the step-6 grant can be made; spend scopes in step 4 come back in `dropped_scopes` with `WALLET_PROOF_REQUIRED`, which is expected). Then, once the step-8 handle gate is cleared, report the borrower as **onboarded but not spend-ready** and tell the operator a wallet or bank account must be connected before paying. Do not ask the borrower for a wallet signature to make the step pass. If `next_actions` instead lists `PROVE_WALLET`, the wallet is registered but unproven — **do step 2**, do not treat it as the no-wallet skip
2. Wallet proof — skip if `wallet_proof_verified` is already true, or step 1’s `next_actions` ask to `CONNECT_WALLET` (the borrower has no wallet). A `PROVE_WALLET` action (from step 1 or `get_context`) means the wallet is registered and only its proof is missing, so do the proof even when `next_actions` is present. Otherwise `request_signature_challenge` → borrower signs EIP-712 off-device in this same turn → `submit_signature`. Never fabricate a signature, and do not insert a yes/no chat question before the challenge
3. `get_borrower_status`
4. `request_borrower_token` immediately with `spend:intent:create`, `policy:evaluate`, `signing:request`, `payment:read`, **`credit:facility:accept`**, `handle:claim`. Store `token_requested_at` + `expires_in`. Do **not** ask the operator, and do **not** wait for a chat reply, before `request_borrower_token`. `whoami.scopes` of `borrower:token` is the OAuth JWT, not expiry. A later pay refreshes only when this chat has no successful token newer than 12 minutes — `{SKILL:sohopay-x402}`
5. Protocol V2 workload key — **route keygen + PoP to the signer**, never hand-roll crypto: [references/workload-key.md](references/workload-key.md) (requires step 1). Skipping step 1 → `TERMINAL_NOT_OWNED`. Run this during onboarding, not on first pay
6. Agent grant — `{SKILL:sohopay-authorize-agent}` immediately after the key. Open the consent URL in this same turn. Onboarding is incomplete until the grant is ACTIVE. Do not invent a dummy `prepare_x402_payment` to poll
7. `POST /api/v1/auth/authorization-context` before privileged tools
8. Handle (**required gate**) — only **after** steps 4–6 (never a chat question before the token). Onboarding is **incomplete until a handle is claimed**. If step 1's `register_borrower` returned `handle: null` with `next_action: "claim_handle"`, present its `suggested_handles` and ask the borrower to pick one or propose their own; for a custom handle, `check_handle_availability` first. Show the exact handle and get an explicit yes (one allowed chat question), then `claim_handle` (write, `idempotency_key`). Recoverable errors → offer more candidates and keep going. When candidates are exhausted, or `handle:claim` was never granted, STOP and report — do **not** report the borrower as onboarded. Details: [references/handle-claim.md](references/handle-claim.md)

If `get_context` returns an `onboarding` section, or a next action with `handoff_type: "OPEN_URL"` (`COMPLETE_PROFILE`, `CONNECT_WALLET`, `CONNECT_BANK`, `EVALUATE_CREDIT`, `REVIEW_CREDIT_OFFER`), that action is a borrower step on the SohoPay consent site. For `CONNECT_WALLET` or `CONNECT_BANK`, call `start_browser_handoff` (write, fresh `idempotency_key`; no action argument) and open the returned `open_url` for the borrower verbatim. When the borrower says they are done, call `get_context` again. If that tool is not listed, report the step with no link. On `409 NO_BROWSER_HANDOFF`, re-read `get_context`. After `expires_at`, call again with a new key. Do not call it while `PROVE_WALLET` is listed, unless the borrower chooses a bank. Connecting wallet or bank is evidence only — it does not activate spendable credit until facility acceptance. A `REVIEW_AND_ACCEPT_FACILITY` next action means call `review_facility_offer` (write, fresh `idempotency_key`) and open the returned `open_url` verbatim. Do not invent `/facility/accept`. A sign-in URL means send the borrower there and call again with the same idempotency key only for that attempt. Other `OPEN_URL` steps: report what is needed and never invent a link. Never ask for a legal name, date of birth, bank details, or a passkey in chat. Keep doing any `PAY`, repayment or handle action listed alongside it. `PROVE_WALLET` is the exception: it is not a browser step. It means the wallet is registered and only its proof is missing, so do step 2; `CONNECT_WALLET` means the borrower has no wallet. These hints never change the numbered steps. Details: [references/onboarding-context.md](references/onboarding-context.md)

Dropped scopes are not fatal — re-request after gates complete. Scope table: [references/scopes.md](references/scopes.md). Operate: `{SKILL:sohopay-human-direct}`. Warm pay after the grant is ACTIVE: `{SKILL:sohopay-x402}`.
